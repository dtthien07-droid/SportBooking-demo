PROJECT STRUCTURE AND CODE GUIDE

PHẦN 1 Tổng quan dự án

1.1. Giới thiệu

SportBooking là website đặt sân thể thao theo khung giờ, gồm hai vai trò User (khách đặt sân) và Admin (quản trị). Khách tìm sân theo môn/quận/ngày/giờ, chọn một hoặc nhiều khung giờ liền kề trên cùng sân và ngày, đặt cọc 50% hoặc trả toàn bộ qua cổng thanh toán giả lập, nhận một vé QR cho cả đơn, hủy đơn theo chính sách hoàn tiền, xem lịch sử và thông báo trong app. Admin quản lý cơ sở/sân/khung giờ/giá, người dùng, dashboard và hủy đơn sự cố (hoàn 100%).

  • Dữ liệu khởi tạo: 29 cơ sở tại 6 quận Hà Nội (cầu lông 10, bóng đá mini 8, pickleball 11) từ khảo sát thực tế — infra/data/khao-sat-san.xlsx, nạp bằng infra/database/seed-facilities.js.
  • Múi giờ nghiệp vụ: UTC+7 (Asia/Ho_Chi_Minh); giờ vàng 17:00–21:00 giá cao hơn.
  • Realtime bằng polling 5 giây (không WebSocket/SSE).
  • Phạm vi mở rộng (chưa triển khai): tìm đối/ghép đối (FR-13–15), đánh giá sân (FR-18), quên mật khẩu/RSS/email — xem Phần 8.

3.5. Lý do chọn kiến trúc

  • Monolith cùng origin — chủ động loại bỏ lỗi CORS: app.js:101 dùng express.static phục vụ frontend ngay trong tiến trình API, nên trình duyệt gọi API cùng origin — không phát sinh preflight CORS, không cần cấu hình cross-origin. Một lệnh npm start chạy toàn hệ thống, triển khai và sao lưu đơn giản.
  • Bảo mật phiên theo chuẩn cookie: cookie phiên đặt httpOnly: true + sameSite: 'lax' (session.cookie.js:23–24). HttpOnly khiến JavaScript không đọc được cookie (giảm rủi ro XSS đánh cắp phiên); SameSite=Lax chặn gửi cookie theo yêu cầu cross-site (giảm rủi ro CSRF). Cùng origin là điều kiện để bộ đôi này hoạt động đúng mà không cần nới lỏng chính sách.
  • Polling 5s + ETag/304 — tối ưu băng thông, đúng quy mô: middleware admin-etag.js băm SHA-256 payload (loại server_time để tránh nhiễu) thành weak ETag; khi If-None-Match khớp, server trả 304 không thân — chu kỳ 5s gần như không tốn băng thông lúc dữ liệu đứng yên. Nhịp 5s đủ mịn cho nghiệp vụ đặt sân (trạng thái slot thay đổi theo phút), không phải duy trì kết nối WebSocket/SSE và hạ tầng push phức tạp.
  • Tách routes / service / repository theo miền (auth, facilities, bookings, notifications, admin) — mỗi tầng test độc lập được, bằng chứng là 325 test đạt (Phần 9).
  • An toàn dữ liệu: mọi thao tác ghi quan trọng dùng transaction + khóa dòng; quyền kiểm tra ở middleware và trong service (chủ đơn). Job nền chạy trong tiến trình web theo thiết kế idempotent (test xác nhận chạy lại không đổi dữ liệu) — không cần hàng đợi riêng ở quy mô đồ án.

Ý chính khi Demo

  • Một tiến trình Express phục vụ cả frontend tĩnh lẫn REST API cùng origin → không CORS; cookie HttpOnly + SameSite=Lax bảo vệ phiên.
  • Chống đặt trùng bằng transaction + UPDATE có điều kiện (affectedRows) — minh họa bằng Hình 3.2.
  • Realtime là polling 5 giây có ETag/304: dữ liệu không đổi thì trả 304 không thân, tiết kiệm băng thông; thông báo ghi cùng transaction sự kiện.

4.5. Ví dụ truy vấn thật trong source

① Khóa khung giờ nguyên tử — backend/src/bookings/bookings.repository.js (lockTimeSlotsForBooking)

UPDATE time_slots
SET status = 'LOCKED',
    current_booking_id = ?,
    lock_expires_at = ?,
    updated_at = UTC_TIMESTAMP(3)
WHERE id IN (?, ?, ...)
  AND (status = 'AVAILABLE'
       OR (status = 'LOCKED' AND lock_expires_at <= UTC_TIMESTAMP(3)));
-- Service kiểm tra affectedRows = số slot yêu cầu; thiếu → ROLLBACK + 409 SLOT_UNAVAILABLE

② Hạn giữ chỗ lấy từ giờ server — bookings.repository.js (createHoldDeadline)

SELECT DATE_ADD(UTC_TIMESTAMP(3), INTERVAL 10 MINUTE) AS lock_expires_at;

③ Điều kiện “khung chọn được” dùng chung mọi lưới giờ — backend/src/facilities/slot-availability.js (selectableSlotPredicate)

(ts.status = 'AVAILABLE'
  OR (ts.status = 'LOCKED' AND ts.lock_expires_at IS NOT NULL
      AND ts.lock_expires_at <= UTC_TIMESTAMP(3)))
AND c.is_active = TRUE AND f.is_active = TRUE
AND (f.opening_time IS NULL OR ts.starts_at >= f.opening_time)
AND (f.closing_time IS NULL OR ts.ends_at <= f.closing_time)
AND TIMESTAMP(ts.service_date, ts.starts_at)
    >= DATE_ADD(DATE_ADD(UTC_TIMESTAMP(3), INTERVAL 7 HOUR), INTERVAL 15 MINUTE)

Cả ba truy vấn đều tham số hóa (placeholder ?), không ghép chuỗi giá trị người dùng → chống SQL injection. Alias SQL được validate bằng regex trước khi ghép.

6.7. Điểm kỹ thuật đáng chú ý

  • Transaction + khóa dòng: mọi thao tác ghi đơn (tạo/hủy/thanh toán/hủy sự cố) chạy trong transaction, khóa user/booking/payment/slots bằng SELECT ... FOR UPDATE theo thứ tự id cố định để giảm deadlock.
  • Tiền BigInt: tổng đơn = tổng giá từng khung; cọc 50% làm tròn lên (total + 1n) / 2n; hoàn 50% làm tròn xuống paid / 2n.
  • Mã đơn: SPB-YYYYMMDD-xxxxxx sinh từ crypto.randomBytes, alphabet bỏ ký tự dễ nhầm, thử lại tối đa 5 lần nếu trùng.
  • ETag admin: sha256 JSON response (trừ server_time) → If-None-Match trả 304, giảm tải polling 5s (admin-etag.js).
  • Audit: mọi thao tác ghi admin ghi admin_audit_logs trong cùng transaction; xuất Excel cũng bị audit.
  • Xuất Excel an toàn: ô bắt đầu bằng = + - @ được thêm dấu nháy đơn chống formula injection; giới hạn 5000 dòng.
